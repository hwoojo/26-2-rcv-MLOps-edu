# 스테이징?
스테이징이 있는 목적은 내가 뭘 커밋할지를 결정하기 위함이다. 그러니까 예를 들어서...
```
file1.txt
file2.txt
file3.txt
```
를 수정을 했고, file1만을 일단 커밋하고 싶다. 이런 경우에 `git add file1.txt`를 통해서 스테이지에 올리고, 커밋하는 식으로 해서 선택적 커밋을 할 수 있겠다.

그럼 내리는 법은? `git rm`이 있는가 하면 `git reset`도 있다. 책에선 reset을 더 쓴다고 하는데 어떤 차이가 있을까? 이유가 있으니까 선택을 하겠지.

`git rm`은 원격저장소와 로컬저장소의 staging area에서 파일을 내리면서 **실제 파일도 삭제한다**
그래서 보통 --cashed 옵션을 달아서 원격저장소에 잘못된 파일을 올렸을 때 파일도 지우고 staging area에 내리려고 그러는 것

그래서 그냥 staging area에서 내리기만 하겠다면 reset을 쓰는 게 좋다. 프로젝트 하나 날려 먹고 싶지 않다면.

물론 reset은 그게 다가 아니긴 하다. 브랜치를 되돌리는 곳에도 쓰인다. 
`git reset --hard`를 통하면 현재 브랜치를 지정한 커밋으로 돌리게 된다. 이 뒤에는 해시 값이 들어감.

엥? 쟤는 그러면 스테이징 관리 툴이 아닌가요?
네. **HEAD / 스테이지(index) / 작업 트리(working tree)를 특정 상태로 되돌리는 것**이 본질임

# 브랜치는 언제 쓸까
협업을 한다면 브랜치를 밥 먹듯이 쓸 텐데, 물론 팀원과 협의해서 파면 좋겠지만 일반적으로 뭐 이런 게 있겠다.
1. 새로운 기능 추가
	1. 이건 당연히 그렇다. main 브랜치의 최신 커밋으로 개발을 할 텐데, 여기다가 바로바로 수정해서 올릴 게 아니라 새로운 브랜치로 구분한 다음에 새로운 기능을 추가한다. 이후 개발, 코드 리뷰, 테스트, 모두 다 통과한다면 main으로 병합할 수 있겠다.
2. 버그 수정
	1. 버그 수정은 한다고 해서 충돌이 안 생긴단 보장은 없다. 따라서 main에다가 냅다 바로 수정할 게 아니라 브랜치를 통해 구분한 다음에 이 또한 테스트를 거친 다음에 병합할 수 있겠다
3. 병합과 리베이스 테스트
	1. 오히려 병합을 테스트하기 위해서 브랜치를 구분할 수도 있겠다. 만약에 병합을 했더니 문제가 발생해버린다면 그 브랜치를 지우면 되기 때문이다. 메인에다가 했다가 큰 화를 불러오는 것보다.
4. 이전 코드 개선
	1. 기능 구현 말고 함수 로직 개선 등 코드를 더 낫게 하기 위해 뭔가 짤 수도 있지만, 새로 브랜치를 만들고 통합하는 편이 낫다. 단순히 코드 아래에다가 주석 달고 새로운 코드를 붙이는 것보다. 그러면 이전 코드를 지우고 새 코드를 작성할 수 있고, 필요하다면 이전 커밋을 확인해 새 코드를 확인할 수도 있다.
5. 특정 커밋으로 돌아가고 싶을 때
	1. 단순히 바로 메인을 몇 단계 전으로 롤백하는 것보다 브랜치를 하나 만들고 돌려버리는 식으로 해서 이전 것과 병렬 진행하는 것도 좋다.

# Git alias?
사실 저런 표현은 없음. 정확히 표현하자면 revision syntax, 혹은 revspec(revision specification)이라고 부르는 것들

`HEAD~숫자`, `HEAD^숫자` 같은 형식인데
- `HEAD~1` → HEAD의 첫 번째 부모
- `HEAD~2` → 첫 번째 부모 → 또 첫 번째 부모
- `HEAD~3` → 첫 번째 부모를 3번 따라감
-> 아빠 커밋, 할아버지 커밋, 증조 할아버지 커밋...

- `HEAD^` = `HEAD^1` = 첫 번째 부모 
- `HEAD^2` = 두 번째 부모 
- `HEAD^3` = 세 번째 부모
-> 부모가 여러명임


# merge와 rebase
비슷한 이 두 녀석을 알아보자
```
A---B---C------  
     \        
      D------E
```
뭐 이런 환경이라고 하자

merge는 이런 느낌
```
A---B---C------M  main
     \        /
      D------E
```
D? E? 너희 다른 브랜치였던 거 인정. M에 합쳐. 

rebase는 이런 느낌임
```
A---B---C---D'---E'
```
그냥 언뜻 봐서는 아, 그냥 인정 안 하고 하나로 합치기? 인데.
뭐 표면적으로는 그렇긴 한데 사실은 저 D, E는 기존 D, E를 지우고 새로 만든 복제품 D', E'이다.
왜 복제품이냐? 일단 식별하는 해시가 다르다.
그럼 왜 해시가 다르냐? 부모가 다르기 때문에 얘내들을 '온전히 같은 커밋' 이라고 말할 수 없다.
그러나 다른 자료 구조라든가 이런 것들은 기존 D, E와 같으니 다르다고도 할 수 없다.

그럼 리베이스는 다 합쳐버리는 것 같은데 왜 쓰느냐? 로컬 브랜치를 깔끔하게 정리하고 싶을 때 사용하는 것임. 원격 저장소에 대해서는 웬만해서는 쓰지 말 것.

# 긴급한 버그 처리 시나리오
1. (옵션) 오류가 없는 버전 (주로 Tag가 있는 커밋)으로 롤백
2. 메인 브랜치로부터 핫픽스 브랜치를 생성
3. 빠르게 소스 코드를 수정하고 테스트
4. 메인 브랜치로 빨리감기 병합 및 배포
5. 개발중인 브랜치에도 병합 (이건 충돌 가능성 높음)

문제는 이 5번, 개발중인 브랜치에도 병합이다.

	  D------E << 여긴?

이런 경우에 3-way 병합이 요구된다.

따라서 파일을 최종으로 수정한다음에 git add를 시키면 된다

# 인증 관리하기
Git에는 인증 문제가 종종 터지는 경우가 있다. 패닉하지 말고 차근차근 생각해 보자.
1. Git 자체에 인증 시스템이 없기도 하다
2. 그러나 GitHub 같은 원격 서버라든가
3. SSH / HTTPS 등 보안이라든가
4. 자격 증명 저장소 같은 게 있다든가
이런 것이 있어서 충돌이 날 수도 있다.

일단 알아야 하는 것

윈도우 자격 증명이란 무엇인가?
우리가 어떤 프로그램이라든가 그런 것에 매번 로그인하지 않도록, OS 차원에서 ID와 비밀번호를 가지고 있는 것이다. 깃허브 계정을 만약에 git을 통해서 로그인 시켰다든가 한다면 이 자격증명, Credential에 저장이 된다. 이 덕에 우리가 한 번 로그인을 해두면 컴퓨터를 끄고 키든 간에 계속해서 유지가 되는 것

따라서 git 또한 어떤 자격 증명 관리자를 통하면 접속할 수 있을지 알아야 한다. 애초에 HTTPS 자체가 그런 보안을 가지고 있는 형태기 때문. 따라서 어느 자격 증명 관리자를 통하면 될지는 `git config credential.helper` 과 같은 명령어를 통해 볼 수 있다.

물론 무조건 이걸로 인증하는 건 또 아니다. 나 같은 경우에는 gh를 통해서 인증하도록 되어있다. OS 바이 OS고 그 안에서도 나 같은 방식을 쓸지 SSH를 쓸지는 또 미지수다.

아무튼 윈도우의 경우에서는 이게 꼬여버린다면 윈도우 설정에서 자격 증명을 날리는 걸 통해서 가능하다. 
원래라면 git push를 했을 때 로그인 창이 뜨고, 그 이후엔 문제 없이 잘 지내다가 꼬인 것일 텐데 이 초기화를 통해 다시 로그인할 수 있게 해준다. 이런 경우 보통 로그인 토큰이 만료되거나 했을 수도.

macOS라면 키체인이라는 암호 관리자가 있기 때문에 될 텐데, 리눅스 같은 경우는 너무나 다양한 가능성이 있다. DE가 제공하는 암호 관리자마다 다르기 때문. GNOME이라면 keyring, KDE라면 또 다른 암호 관리자, 혹은 또또 다른 방식을 쓸 수도 있는데

1. cache를 통해서 잠시 동안 로그인 정보를 캐시에 저장해서 push
2. store이라는 리눅스 자체 기능을 통해서 로그인 정보를 영구 저장

하지만 캐시는 지정한 시간 뒤에는 사라져버리고
store은 .gitconfig에 평문으로 암호가 저장된다

그렇다면?
역시나 SSH를 이용하면 된다. 바로 SSH 키를 받는 방식.
`ssh-keygen`을 통해서 SSH 키를 하나 발급을 받아 보자. 그렇다면 두 가지 파일이 만들어진다. 1번, 퍼블릭 키. 2번, 프라이빗 키.

퍼블릭 키는 자물쇠 같은 거고, 프라이빗 키는 진짜 열쇠 같은 느낌
따라서 ~.pub 파일은 어디다 등록하는 경우가 있을 수 있어도 프라이빗 키는 보안에 신중을 가해야 한다.

깃허브에 키 등록하는 법은 뭐 그냥 설정 가면 있으니까 됐고

그 다음엔 열쇠를 열쇠고리에 넣어 놔야 컴퓨터가 알아서 문 딸 수 있다. 그건 보통 ~/.ssh/config 수정이 필요하다. 

```
Host nas
    HostName 123.45.1.65
    User hwoo
    IdentityFile ~/.ssh/id_ed25519

```
이런 식. 보면 알겠지만 저 IdentityFile이 키 파일의 위치다. 저건 프라이빗 키 파일.

사실 이건 git 뿐만 아니라 이곳저곳 쓰이니까 알아두면 좋다!
