# Linting
코드를 돌리기 전에, 코드에서 생겨날 수 있는 문제들을 감지하고 잡아줌. 

이런 나쁜 코드 패턴 같은 건 linter rules 라는 특정 규칙을 통해서 찾아냄. 물론 좋은 코드를 잘못된 코드라고 말할 수도 있기는 있고. 

보통은 바로 자동 수정이 가능한 코드들도 있고, 아니면 사용자가 확인하고 수동으로 이거 바꿔라 라고 명시해주면 바꿀 수 있을 코드들도 있고, 인간이 직접 리뷰를 해야 하는 경우들도 있고.

추후에는 뭐 자동으로 Linting을 켜두고 볼 수도 있고, 어떤 줄에서 `#noqa: {오류코드}`같은 것으로 안 보이게 해줄 수도 있음

웬만하면 온라인에 공개되어서 누가 데이터베이스처럼 수많은 규칙들을 저장해둔 걸 이용하기도 하지만, 반대로 내가 규칙을 추가해 줄 수도 있음.

또한 코드를 찾을 때, 기존에 했던 방식처럼 grep을 이용할 수도 있겠지만 코드 작성하며 line break라든가, 이런 것 때문에 grep에서 안 잡힐 수도 있음. 그래서 편리한 건 semgrep이라는 프로그램. semantic-grep이다. grep처럼 단어 수준에서 찾는 게 아니라 그런 형태를 보고? 정말 의미론적인 것으로 찾는 게 아닌가 싶다

# Testing
여러가지 테스트 방법이 있는데
- intergration tests -> 모듈이나 서비스 사이 간 작동이 원활한지
- functional tests -> 전체적인 프로그램이 내가 원하는대로 작동이 되는지
- test-driven development -> 테스트를 먼저 적고 필요한 코드를 작성하는 형태
- regression test -> 이전에 잘 되던 기능이 코드 수정 이후에도 잘 되는지를 테스트
- property-based test -> OJ 시스템들 처럼 프로그램이 항상 만족해야 하는 성질을 정하고 다양한 입력을 자동 생성해서 테스트 
등등이 존재할 수 있다고

code coverage라고 하면서 테스트를 돌렸을 때 내 코드 중 얼마나 많은 부분이 실제로 실행됐는지 보는 방법도 있음. 이런 걸 해주는 툴도 있고, 이런 부분에서 LLM도 잘 이용될 수 있다고. 그러나 잘한다와 완벽하다를 구분할 필요는 있다.

Pre-commit hook이란 것도 있음. 이거는 코드에서 실행되기 전에 이런 테스트 절차, 즉 property-based test를 통해서 프로그램이 잘 유지되나를 먼저 볼 수 있음. 그래서 특정 인풋에서 만약 제대로 안 된다면 아예 커밋 자체를 못 하게 해버릴 수도.

# Command runners
뭐 alias 같은 거 만들 수 있고 이런 종류인데... 그럼 Shell은 대체 어떤 차이가 있는 걸까? shell도 뭐 bashrc 파일에 alias 지정해서 할 수 있을 텐데?

중요한 점은 이런 걸 파일로 만들어서 배포할 수 있단 것이다. 즉, 내가 어떤 프로젝트에 just라는 command runners의 justfile을 만들어 둔다면, 누구든지 그 프로젝트를 복사해오면 그 alias를 쓸 수 있단 것이다. 따라서 굉장히 복잡한 코드를 하나하나 치거나 복사하라고 할 필요 없이, 이런 식으로 justfile 내부에 있는 alias를 이용할 수 있단 것.
