패키지를 만드는 이유가 뭐냐, 하면 결국 어떤 프로그램은 단순히 그것 하나만 있는 것이 아니라 그것에 종속되는 종속성 프로그램들이 여러가지가 있기 때문임. 그런 종속성 프로그램과 환경이 존재하기 때문에, 이것에 대해 다루는 것이 패키지와 shipping이라고 할 수 있겠다.

# Dependencies & Environment
예를 들어 파이썬에서 어떤 모듈을 임포트를 했다고 가정했을 때에, 만약에 그게 빌트인 모듈이 아닌 이상 그걸 설치를 하고 임포트를 해야 함. 이 경우 pip를 많이 이용함. 

```bash
pip install request
```
뭐 이런 걸로.

이런 pip와 같은 걸로 무언가를 설치하면 그 프로그램만 설치하는 것이 아니라 이 프로그램을 쓰기 위해 필요한 다른 모듈과 같은 것을 설치하게 됨. 이런 것을 종속성이라 할 수 있겠음.

```
pip list | grep requests
```
같은 걸로 어떤 버전이 설치되어있나 볼 수 있기도 하겠고

이건 파이썬으로서의 예시지, 언어별로, 그리고 환경별로 다 다를 수 있을 거임.

특히 프로그래밍 언어는 단순히 표현 방법만 바뀌는 게 아니라 이에 따른 철학이 바뀌고, 어떻게 적느냐가 다 달라지기 때문에 잘 고려를 해야 함

다른 예시로 레이텍, LaTex가 있음. 얘는 기본적으로 LaTex를 설치할 때 많은 패키지들을 같이 설치하도록 함. 때문에 LaTex를 이용하면서는 뭔가 추가적인 모듈이나 이런 걸 설치할 일이 잘 없어짐. 

이런 종속성 프로그램을 많이 설치하면 설치할 수록, 각 프로그램이 바라는 종속성 프로그램의 버전이 다를 수 있음. 뭐 넘파이는 1.25 이상 2.0 아래 버전이 필요하다고 했을 때에 이 모든 것이 모든 프로그램과도 적용될 것이란 건 쉽지 않음.

따라서 파이썬에서도 지원하는 것 중 하나가 가상환경임. 

```shell
python -m venv myvenv
source myvenv/bin/activate
```
같은 걸로 파이썬 가상환경을 만들어서 분리할 수 있음. 

이러면 이 가상환경 내부에서 `pip install`을 이용해서 모듈 / 패키지를 깔아서 내가 필요한 종속성 프로그램만을 설치할 수 있게 됨

탈출은 `deactivate`

이런 문제가 당연히 하루이틀이 아닐 테고 최근에 들어서는 더 나아지고 있음. 그 중 하나가 `uv`임. 
`pip` 뿐만 아니라 다양한 문제를 해결해줄 수 있음.

```
uv venv myvenv
uv pip list
uv pip install ...
```
뭐 이런 식으로. 대신 속도도 엄청나게 빠름. 

단순히 종속성 프로그램만의 문제가 아니라 언어 자체의 버전이 문제가 될 수도 있음. 파이썬이 3.12가 필요한데 3.11이 설치되어있따든가. 뭐 반대일 수도 있고.

이 경우에도 uv로 해결이 가능. `uv venv --python 3.12 venv312`같은 식으로 적어서 파이썬 버전에도 차이가 있는 가상환경을 구성할 수 있음

# Artifacts & Packaging
문제는 단순히 내가 쓰는 것에서 끝이 아니라 다른 사람에게 공유함에도 있음

이런 패키지를 인스톨할 수 있게 하려면 파이썬의 문법?을 따라서 해야 함.
```toml
[project]
name = "greeting"
version = "0.1.0"
description = "A simple greeting library"
dependencies = ["typer>=0.9"]

[project.scripts]
greet = "greeting:cli"

[build-system]
requires = ["setuptools>=61.0"]
build-backend = "setuptools.build_meta"
```
이런 식의 .toml 파일을 만드는 것으로.

버전, 종속 프로그램, CLI, 등등... 다양한 것을 설정해줄 수 있다.

이런 식으로 나만의 패키지를 만들 수 있는 것임

물론 이런 거는 소스코드와 pre built 패키지를 구분할 줄도 알아야 함. 단순히 소스코드를 다 주고 만들게 할 필요도 없이, 어떤 특정 파일만을 가지고도 패키지를 설치할 수 있음.

예를 들어 깃허브에 가서 어떤 프로그램을 보면 보통 release가 있음. 이런 건 단순히 소스코드를 다 때려 넣은 게 아니라 어떤 프로그램을 설치할 때 필요한 것들만 담아둔 것임. 단, OS / CPU Architecture에 맞게.

다른 방식으로는 Wheel이란 게 있음. 어떤 wheel 파일을 실행시키면 거기에 해당되는 모든 파일이 쭈루룩 설치가 되는 형태. 이건 zip 압축 파일과 닮아서 그 안에 뭐 메타데이터 같은 게 들어가있고, 이런 형태라고 함.

# Releasing & Versioning
어떤 프로그램을 만들고 배포함에 있어서, 중요한 점들이 있음

1. 종속 프로그램 버전을 적어주는 것
toml 파일에도 해당되는 것이긴 한데 여기서 문법도 또 각각 다름
```
[project]
dependencies = [
    "requests==2.32.3",  # Exact version - only this specific version
    "click>=8.0",        # Minimum version - 8.0 or newer
    "numpy>=1.24,<2.0",  # Range - at least 1.24 but less than 2.0
    "pandas~=2.1.0",     # Compatible release - >=2.1.0 and <2.2.0
]
```
이런 식임. 무조건 같아야 함, 최소 이 버전이어야 함, 이 사이 버전이어야 함, 이 근처 버전이면 됨. 뭐 이런 정도

이유 중 하나는 종속 프로그램이 단 하나가 아니고 종속 프로그램의 종속 프로그램 별로 또 버전이 갈라질 수 있기 때문임. 이런 걸 보려면 `uv tree`명령어를 통해서 트리 형태로 볼 수 있으니 이 방법을 이용해봐도 좋음

버전을 만드는 것에도 방법이 있고, 가장 유명한 것은 Semantic Versioning이라고 함
변경을 총 3개로 볼 수 있음
1. 메이저
2. 마이너
3. 패치
메이저는 어떤 특정 부분은 안 될 수도 있을 정도로 큰 변경
마이너는 그래도 기존 있던 것은 다 되고, 추가 기능이 있는 정도
패치는 뭐... 간단한 문서 수정 정도로 가벼운 변경

버전을 적어주는 것에 안 좋은 것은 굉장히 넓은 범위로 잡아주는 것임. 유명 프로그램을 구경하면 알겠지만 굉장히 좁게 버전들을 잡아줌. 단순히 넓다고 다 좋은 건 아니고...

그래서 지금 내가 무언가를 만든 이 환경을 딱 사진 찍듯 찍어주는 명령어도 있음. 
`uv lock`이 그런 느낌임. 얘는 어떤 패키지, 버전, 소스, 등등... 이걸 .lock이란 파일로 만들어주고, 다른 사람들은 그 파일을 받고 uv sync라는 명령어를 통해서 어려운 과정 없이 딱 설치가 가능해짐. 

물론 만능은 아니고 한계는 존재함.
만약 이게 프로그래밍 언어 패키지의 영역을 벗어난다면 더 넓은 패키지 관리자가 필요함. Nix 같은. 

예를 들어서 파이썬은 C 컴파일러를 종속으로 가짐. 근데 파이썬 버전에 따라서 C 컴파일러 버전 또한 다를 수도 있음. 이러면 이제 단순히 패키지를 관리하는 것을 넘어서 컴퓨터 전체를 다뤄야 함.

Nix, NixOS는 이런 부분을 좀 더 해소해주는 패키지 관리자임. 좀 더 찾아보면 좋음.

CuPy란 게 있음. 넘파이를 GPU에 더 쉽게 올려주는 뭐 그런 거임. 이런 것도 CUDA Toolkit에 대하여 각각의 호환 버전이 존재함. 

얘는 CUDA에 강한 종속이 있기 때문에 CUDA 버전 별로, OS 별로, 아키텍쳐 별로 release가 다 있다고 함.

미친듯이 파일이 많기 때문에 이런 건 당연히 좋진 않음. 그러면 어떤 게 있으면 좋을까

# VMs & Container
Virtual Machine, 가상머신을 이용하는 것임.

단순히 어떤 환경을 분리하는 수준이 아니라 정말 모든 OS 자체를 가상으로 담기 때문에 환경을 좀 강하게 조절할 수 있음. 

Containerization. 컨테이너화 또한 같은 이유임. 이것 또한 OS 수준의 가상화를 해줌. 가상 머신에 컨테이너화까지 할 수도 있음. 보통 가상 머신은 리눅스 계열을 이용하기는 함.

이런 컨테이너화에서 가장 유명한 거라고 하면 당연 도커일 것임. 외에는 쿠버네틱스도 있을 테고.

```shell
docker run -it python:3.14 python
>>>
```
이런 식으로 그냥 파이썬 돌리듯이 나오지만 사실은 이 장치 안에서 분리가 되어서 컨테이너 내부에서 돌아가는 형태가 된다. 

즉 다양한 프로그래밍 언어나 이런 것들을 할 수 있단 것임 유연하게 도커로 돌릴 수 있음

근데 뭐 파이썬? 뭐 이런 거 공식적으로 도커 이미지가 있다? 좋다. 근데 문제는 내가 하고자 하는, 내가 만들고자 하는 어떤 프로그램에 맞는 종속 프로그램을 나만의 도커 이미지를 만들어야 함.

도커 이미지는 얘내 자기만의 문법을 씀. 

```dockerfile
FROM python:3.12
RUN apt-get update
RUN apt-get install -y gcc
RUN apt-get install -y libpq-dev
RUN pip install numpy
RUN pip install pandas
COPY . /app
WORKDIR /app
RUN pip install .
```
이런 느낌쓰

이러고 이제 뭐 `docker build -t {이름} {디렉토리}` 같은 형태가 되면 만들 수 있음

# Servicies & Orchestration
지금까지 필요한 것은 도커 컨테이너로 주어질 수 있는 특정 종속성 프로그램이었더라면, 내가 어떤 서비스가 필요할 수도 있다. 이 경우에는 이 서비스라 하는 것은 자기만의 도커 컨테이너를 먹을 정도의 어떠한 프로그램인 것이다. 뭐 데이터베이스라든가. 

Postgres라는 걸 이용하고 운에 맡겨서 문제가 없길 바라거나, 아니면 컨테이너간의 소통을 할 수 있도록 만들어주는 방법이 있겠다.

예시로 웹앱을 하나 만든다고 했을 때
어떤 방문자가 들어왔을 때 오늘 얼마나 들어왔는지 카운트를 세고 그걸 보여주는 웹앱이라고 했을 때, 그리고 이 카운트 하는 것이 따로 DB가 있다고 가정을 해보자. 그러면 웹앱이 있는 컨테이너에서 모든 걸 다 하는 게 아니라 DB가 있는 컨테이너에게 리퀘스트를 보내게 된다. 

그럼 이 두 컨테이너를 어떻게 소통하게 할 수 있나? 뭐 엄청나게 많은 명령어가 있긴 하다. 그리고 동시에 이렇게 서비스를 하나 만들고 이걸 소통하게 만들 수 있는 파일 또한 있다. 이것도 자기만의 언어?를 쓴다고. 

이러고 이제 `docker compose up`으로 만들 수 있고

이런 서비스들을 관리하는 게 orchestration. 리눅스라면 systemd가 가장 유명하다. 얘도 자기만의 문법이 있다고... 이런 것에는 LLM을 적극 이용하라고 추천하기도 한다.
